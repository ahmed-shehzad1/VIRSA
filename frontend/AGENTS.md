# VIRSA Frontend Agent Guide

## Scope

- Work only in `frontend/` unless the user explicitly requests otherwise.
- Do not modify `backend/` or create duplicate backend endpoints. Consume the existing Express API.
- Preserve the Lovable-connected branch history; do not force-push, rebase, amend, or squash published commits.

## Product and architecture

- VIRSA is a private family archive. Keep the distinction between a logged-in `User` and an archived `Person`; a person may have no account.
- Family-scoped API requests require an authenticated bearer token and a real `familyId`. Do not use the mock family or mock user for authenticated application behavior.
- Keep HTTP calls in `src/services/` and expose server state through the existing TanStack Query layer. Components should not scatter Axios requests.
- The existing frontend uses TanStack Router file routes under `src/routes/`, React Query, Axios, Tailwind CSS, and Lucide icons. Follow these patterns before adding dependencies.
- `src/routeTree.gen.ts` is generated by TanStack Router. Never edit it manually.
- `src/data/mock.ts` and the mock resolvers in `src/data/api.ts` are legacy/demo data. Replace them with service calls when a matching backend endpoint exists; do not silently present mock data as persisted data.

## Backend integration

- Backend responses use the envelope `{ success, message, data }`; unwrap and map response data in the service/query boundary.
- The API base is configured with `VITE_API_URL`. Requests use `withCredentials: true`; protected requests must include the access token used by the existing auth service.
- Existing family APIs include people, relationships, tree, profiles, media, memories, timelines, invitations, members, privacy, and story history. Check `backend/src/routes/` before proposing new API work.
- Never trust frontend role checks as authorization. Use them only to shape the UI; handle backend `401`, `403`, validation, not-found, and conflict responses explicitly.
- Keep access tokens and refresh-cookie behavior compatible with the current authentication implementation. Do not replace working authentication without a specific request.

## Validation

Run from `frontend/` after changes:

```powershell
npm run lint
npm run build
```

For focused work, run the narrowest available check first, then both commands before handoff when practical. Use `npm run dev` to manually verify the app. Do not add test infrastructure unless the task requires it.

## Design and UX

- Preserve the established warm archival visual language: Cormorant Garamond/Karla typography, ivory/parchment surfaces, forest primary, and antique gold tokens in `src/styles.css`.
- Reuse existing UI primitives and `src/components/virsa/` components. Keep loading, empty, error, unauthorized, and mutation states visible and accessible.
- Keep family information private by default, avoid exposing sensitive data in URLs or logs, and ensure responsive and keyboard-accessible interactions.
